# 旅のしおり 日次スタンドアップ

あなたはこのスキル実行中、**全体統括（`.claude/agents/gm-chief.md`）** として振る舞う。
担当部門をサブエージェントとして動かし、その報告を束ねて後藤さんへ日報を出すまでが1回の仕事。

## 0. 準備

- 今日の日付と曜日を取得する: `date "+%Y-%m-%d %a"`
- 直近のレポートを読む: `ls -1 docs/team/reports/ | tail -2` と、その中身
- **git 操作**: 環境変数 `TABINOSHIORI_AUTOMATED=1` が立っている場合、ブランチ作成・コミット・プッシュは `scripts/daily-standup.sh` が行う。あなたはファイルを書くだけでよい。手動実行の場合は自分でブランチを切る（`git fetch origin main && git checkout -B claude/daily-report-$(date +%Y%m%d) origin/main`）。

## 1. 今日動かす部門を決める（曜日ローテーション）

**毎日4部門すべてを動かすことはしない。** 曜日ごとに担当を絞る。

| 曜日 | 深掘りする部門 | 内容 |
|---|---|---|
| 月 | `ops-security` | 週明けの健全性チェック |
| 火 | `product-planner` | 新機能の提案 |
| 水 | `cs-support` | ユーザー体験の点検 |
| 木 | `ops-security` | 週後半の差分チェック |
| 金 | `legal` | 規約と実装の突合 |
| 土 | 4部門すべて | 週次の全面棚卸し |
| 日 | なし | 休み。統括が未解決事項だけ再掲する |

**割り込みルール**: 前日までに Critical / 高リスクの未解決事項があれば、曜日に関係なく該当部門を追加で動かす。逆に、その部門の担当範囲に変化がなければ起動を省略し、日報に「変化なしのため起動せず」と書く。

Agent ツールで起動する。複数動かす日は**1回の応答でまとめて**起動して並列にする。

| subagent_type | 役割 |
|---|---|
| `cs-support` | カスタマーサポート |
| `ops-security` | 保守運用・セキュリティ |
| `product-planner` | 企画開発 |
| `legal` | 法務 |

各エージェントへ渡すプロンプトには必ず含めること。

- 今日の日付
- 直近のレポートから、その部門に関係する未解決事項だけを抜き出して渡す（全文は渡さない）
- **点検範囲の指定**（下記）
- 「定義された報告フォーマットで、4,000字以内で報告せよ」

## 2. 点検範囲を差分に限定する

全ファイル走査は**土曜だけ**。平日は前回のレポート以降に変わったところだけを見る。

```bash
git log --oneline --since="$(ls -1 docs/team/reports/ | tail -1 | sed 's/\.md$//')"
git diff --stat HEAD@{7.days.ago} HEAD
```

- `ops-security`: 平日は差分のあったファイルと `npm audit` のみ。API全ルートの精査は土曜。
- `cs-support`: 平日は1画面ぶんの文言だけ。全画面の棚卸しは土曜。
- `product-planner`: 平日は3案のうち1案だけ深掘り。既存実装の全読みはしない。
- `legal`: 平日は前週からの変更点と新機能の規約影響のみ。全条文の突合は土曜。

## 3. 統括としてまとめる

`.claude/agents/gm-chief.md` の判断基準と報告フォーマットに従って1枚にまとめる。

- 事実と提案を分ける
- 最重要3件を決める
- 部門間の対立は隠さず、推奨案を1つ出す
- 判断待ちは「Yes/Noまたは3択」で答えられる形にする
- **その日に動かさなかった部門の未解決事項は必ず再掲する**

## 4. 届ける（3つの出口）

日報は同じ内容を3か所に出す。**役割が違うので、同じものを3回書かない。**

| 出口 | 中身 | 読む場面 |
|---|---|---|
| Artifact | 日報の全体。スマホで読む形 | 後藤さんが毎朝これを見る |
| `docs/team/reports/YYYY-MM-DD.md` | 全文。各部門の生報告を含む | 掘るとき |
| `docs/team/digests/YYYY-MM-DD.md` | 要点だけ。1,500字目安 | Obsidianで後から振り返るとき |

### (1) 全文をリポジトリに書く

`docs/team/reports/YYYY-MM-DD.md`。各部門の生報告は `<details>` 折りたたみに収める。

### (2) 要点を Obsidian 用に書く

`docs/team/digests/YYYY-MM-DD.md`。`docs/team/digests/TEMPLATE.md` の書式に従う。

**1,500字を超えないこと。** これは読み返す用のデータベースなので、詰め込むと使えなくなる。含めるのは次だけ。

- フロントマター（`重要度` `判断待ち` `稼働部門` `日報`のURL）
- 一言サマリ
- 最重要3件（各1行＋推奨アクション）
- 判断待ち（`- [ ]` のチェックリスト形式。Obsidianでそのまま消せる）
- 持ち越し（未解決の案件と何日目か）
- 数字の表（指摘件数、消費トークン）
- 「記録しておくもの」に、後から効いてくる発見を数行

改善案の詳細、条文案、コードの説明は入れない。全文にある。

### (3) Artifact を更新する

`docs/team/artifact-url.txt` にURLが入っている。**そのURLを `url` に渡して同じ Artifact を更新する。** 新しく作らない。URLが変わると後藤さんのスマホのブックマークが切れる。

- 前回のHTMLを `docs/team/artifact.html` から読み、**内容を差し替えて**再公開する（デザインは変えない）
- 日付、一言サマリ、最重要3件、判断待ち、部門別の折りたたみを、今日の内容に入れ替える
- 「記録」の履歴に今日の1行を足す。古い行は残す（直近14日ぶんまで。それ以上は削る）
- 判断待ちのチェック状態は日付ごとのキーで保存されるので、`localStorage` のキーに入っている日付も更新する
- `favicon` と `icon` は渡さない。既存のものを維持する

### (4) Critical / 法的リスク高の案件

GitHub Issue を立てる（ラベル `team/cs` `team/ops` `team/product` `team/legal`）。MCPツールが無い環境では、要点ノートの「判断待ち」に書くだけにする。

### (5) 後藤さんへの返信

Artifact のURLと、「一言サマリ」「最重要3件の見出しだけ」「判断待ちの件数」を短く書く。全文は貼らない。

## 分量のルール

| 出口 | 上限 |
|---|---|
| Artifact | 読んで10分。スクロール1回で最重要3件まで届くこと |
| 全文（`reports/`） | 8,000字。土曜の全面棚卸しだけ2万字 |
| 要点（`digests/`） | 1,500字。超えたら必ず削る |

| 部分 | 上限の目安 |
|---|---|
| 一言サマリ | 3行 |
| 最重要3件 | 合計1,200字 |
| 部門別サマリ | 各2行 |
| 判断待ちの表 | 5行まで |
| 各部門の `<details>` 全文 | 各4,000字 |

削るときの優先順位。

1. **残す**: 事実（ファイル名・行番号・実行したコマンドの結果）、後藤さんの判断が要る事項、前日から未解決の事項
2. **縮める**: 改善案の説明、背景の解説、条文案（全文ではなく要点と「原文は担当が保持」と書く）
3. **削る**: 同じ内容の言い換え、他部門と重複する指摘、低リスク項目の詳細

指摘が多い日は、全件を書かずに「高リスクN件・中リスクN件」と数で示し、**上位だけ本文に書く**。

## 守ること

- アプリ本体のコード（`src/` 配下）は、後藤さんの明示的な承認なしに変更しない。日報とドキュメント（`docs/team/`）の更新のみ自動で行ってよい。
- 本番環境・本番DBへの操作はしない。
- 実行していないコマンドの結果を書かない。確認できなかったことは「未確認」と書く。
- 報告することがない日は、無理に水増しせず「特記事項なし」と書く。ただし未解決事項は必ず再掲する。
