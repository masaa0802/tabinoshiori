# 旅の写真（アクティビティ写真）機能 仕様書ドラフト

- ステータス: ドラフト（承認前）
- 作成日: 2026-09-28
- 対象: A案「あとでまとめて取り込み・自動振り分け」／B案「今」画面からのワンタップ撮影
- 対象外（別仕様書）: 思い出しおり・ムービーの自動生成、2秒動画クリップ、プッシュ通知

---

## 1. 背景と目的

### 背景
setlog（1時間ごとに2秒の動画を撮ると、1日分が自動で1本のVlogになるアプリ）が流行している。しおりには予定ごとに日付・時刻・場所・名前がすでにあるため、旅行中の写真を予定と紐付ければ「章立てされた旅の記録」を自動で作れる。

### 一番の課題：撮る瞬間の手間
「アプリを開く → しおりを開く → 予定を開く → カメラを開く」と4〜5タップかかると、旅行中はまず使われない。
この仕様書では **撮る瞬間に予定を選ばせない** ことを設計の軸にする。紐付けはアプリがあとで自動で行う。

### 2つの入口
| | A案：あとでまとめて取り込み | B案：「今」画面から撮影 |
|---|---|---|
| 旅行中の操作 | なし（標準カメラで普通に撮る） | ホーム画面アイコン → 撮影ボタン |
| 予定との紐付け | 撮影日時（と位置）から自動 | 撮影時点の「今の予定」に自動 |
| 向いている人 | すべての人 | しおりをよく見る幹事タイプ |
| 優先度 | **先に作る（M1）** | 後に作る（M2） |

両案とも同じデータ（`activity_media`）に保存するため、あとで混ぜて使える。

### 成功指標
- 旅行期間を過ぎたしおりのうち、写真が1枚以上あるしおりの割合
- しおり1件あたりの写真枚数
- 自動振り分けの修正率（手動で移動された枚数 ÷ 自動で振り分けた枚数）。目標は20%未満
- A案とB案それぞれの利用比率

## 2. 前提条件（着手前に必要なこと）

### 2.1 GraphQL の認可修正【必須】
`docs/team/reports/2026-09-11.md` の C-2・H-2 のとおり、現状の `/api/graphql` は有効なトークンが1つあれば他グループのデータまで読み書きできる。旅程IDは連番（SERIAL）なので推測できてしまう。
**自撮りを含む写真を扱う以上、この修正が終わるまで本機能は公開しない。**

本機能の写真API（4章）は、`/api/graphql` を経由せず専用のAPIルートで「そのトークンのグループに属する旅程か」をサーバー側で確認する。

### 2.2 既存の `activities.photo_url` との関係
`activities.photo_url` は Google Places の写真を表示するための項目（`ActivityDetailModal.tsx`）。ユーザーが撮った写真とは別物なので流用せず、新しいテーブルに保存する。

## 3. データモデル

### 3.1 新規テーブル `activity_media`

```sql
CREATE TABLE activity_media (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    itinerary_id INTEGER NOT NULL,
    activity_id INTEGER,                      -- NULL = 未分類
    media_type VARCHAR(20) NOT NULL DEFAULT 'image',  -- 将来 'video'
    url TEXT NOT NULL,
    cloudinary_public_id TEXT NOT NULL,
    width INTEGER,
    height INTEGER,
    taken_at TIMESTAMP WITHOUT TIME ZONE,     -- 撮影地の現地時刻（後述）
    assign_method VARCHAR(20) NOT NULL,       -- 'capture' | 'auto_geo' | 'auto_time' | 'manual' | 'unassigned'
    uploader_name VARCHAR(50),
    uploader_device_id VARCHAR(64),
    content_hash VARCHAR(64),                 -- 二重取り込み防止
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    FOREIGN KEY (itinerary_id) REFERENCES itineraries(id) ON DELETE CASCADE,
    FOREIGN KEY (activity_id) REFERENCES activities(id) ON DELETE SET NULL,
    UNIQUE (itinerary_id, content_hash)
);
CREATE INDEX idx_activity_media_itinerary ON activity_media(itinerary_id, taken_at);
CREATE INDEX idx_activity_media_activity ON activity_media(activity_id);
```

- マイグレーションは `hasura-project/migrations/default/9_add_activity_media_table/` に置く。本番用は `travel-planner-prd` 側にも同じものを用意する。
- Hasura のメタデータで `activities` に配列リレーション `media` を追加する。

### 3.2 設計上の決めごと

**位置情報は保存しない**
写真のGPSは、端末上で予定と照合するためだけに使う。サーバーにもCloudinaryにも送らない。画像はブラウザで縮小（再エンコード）してから送るので、EXIFごと消える。

**`taken_at` はタイムゾーンを持たない現地時刻**
`activities.date` / `activities.time` もタイムゾーンを持たない現地時刻で、写真のEXIF（`DateTimeOriginal`）も同じく現地時刻。そのまま比較すれば海外旅行でも時差の計算は要らない。

**アップロードした人の識別**
ログインの仕組みがないため、端末ごとにランダムなIDを `localStorage` に保存して `uploader_device_id` とする。表示名は初回だけ入力してもらう（任意）。

**`content_hash`**
元ファイルの先頭1MB＋ファイルサイズ＋撮影日時のSHA-256。同じ写真を2回取り込んだときに重複を防ぐ。

## 4. API

写真の登録・移動・削除はすべて専用のAPIルートで行う。どのルートでも、次の2点をサーバー側で必ず確認する。

- `x-group-token` が有効なこと
- 対象の旅程（または写真）がそのトークンのグループに属していること

| メソッド | パス | 内容 |
|---|---|---|
| POST | `/api/media/sign` | Cloudinary へ直接アップロードするための署名を発行する。保存先フォルダ `travel-planner/media/{itineraryId}`、形式は jpg/webp のみ、サイズ上限あり |
| POST | `/api/media` | アップロード済みの写真を最大50件まとめて `activity_media` に登録する |
| PATCH | `/api/media` | 写真の予定を付け替える（`activity_id` を変更し、`assign_method='manual'` にする） |
| DELETE | `/api/media/{id}` | 写真を削除する（DBの行とCloudinaryの画像の両方） |
| GET | GraphQL `GetItineraryMedia` | 写真の一覧。2.1の修正後は旅程単位で絞り込む |

**サーバー経由ではなく Cloudinary へ直接アップロードする理由**
既存の `/api/upload` はファイルをサーバー経由で送っている。写真を何十枚もまとめて送ると、ホスティング側のリクエストサイズ上限（Vercel の場合は約4.5MB）とサーバーの処理時間を圧迫するため、署名付きで直接送る方式にする。

**表示用の画像**
Cloudinary の変換機能で出し分ける。
- サムネイル: `c_fill,w_300,h_300,f_auto,q_auto`
- 拡大表示: `w_1600,f_auto,q_auto`

## 5. 共通：ブラウザでの画像処理

`src/lib/media/` に共通モジュールとして置き、A案・B案の両方で使う。

1. **EXIFを読む**（`exifr` を使う。読むのは `DateTimeOriginal` と `GPSLatitude` / `GPSLongitude` のみ）
2. **縮小する**: `createImageBitmap` と canvas で長辺2048pxに縮小し、JPEG（画質0.85）に変換する。1枚あたり約300〜600KBになり、EXIFも消える
3. **アップロードする**: 同時に3件まで。失敗したら指数バックオフで3回まで再試行する
4. **送信待ちの列（キュー）**: 送る前の写真はIndexedDBに保存し、送れたら消す。アプリを閉じても消えず、次に開いたときに送信を再開する

iOS はバックグラウンドでの送信（Background Sync）に対応していない。そのため送信はアプリを開いている間だけ行い、「未送信 3枚」のように状態を画面に出す。

## 6. A案：あとでまとめて取り込み・自動振り分け

### 6.1 入口
- しおり画面に、旅行期間中と旅行後だけ出るバナー「📸 この旅の写真を取り込む」
- 旅行最終日の翌日以降、しおりを開いたときに一度だけ案内のシートを出す
- 予定の詳細シート（`ActivityDetailSheet`）の写真欄にある「＋ 追加」（この場合は振り分けず、その予定に直接追加する）

### 6.2 画面の流れ

```
① 案内               ② 端末の写真選択        ③ 振り分け結果の確認        ④ 完了
┌──────────────┐    ┌──────────────┐    ┌──────────────────┐    ┌──────────────┐
│ 旅の写真を     │    │ (OS標準の     │    │ 42枚を振り分けました│    │ ✓ 38枚 追加   │
│ 取り込む       │ →  │  写真選択)    │ →  │                  │ →  │              │
│              │    │              │    │ 未分類 4枚  [確認] │    │ 送信中 12/38 │
│ 10/3〜10/5の  │    │ 複数選択OK    │    │ ─ 10/3(土) ─     │    │ ▓▓▓▓░░░░     │
│ 写真を選んで   │    │              │    │ 10:00 清水寺  8枚 │    │              │
│ ください      │    │              │    │ [■][■][■][+5]    │    │ 画面を閉じても│
│              │    │              │    │ 12:30 錦市場  5枚 │    │ 次に開いたとき│
│ [写真を選ぶ]  │    │              │    │ [■][■][■][+2]    │    │ 続きを送ります│
│              │    │              │    │ ...              │    │              │
│              │    │              │    │ 期間外 3枚 (除外) │    │ [しおりを見る]│
│              │    │              │    │ [この内容で追加]  │    │              │
└──────────────┘    └──────────────┘    └──────────────────┘    └──────────────┘
```

- ②は `<input type="file" accept="image/*" multiple>` で開く。Webから端末の写真を日付で絞り込むことはできないので、①で旅行期間を大きく表示して選びやすくする。
- ③の「予定の振り分け（6.3）」は端末内で行う。EXIFを読むだけで済むため、アップロード前に一瞬で結果を出せる。
- ③で写真をタップすると選択状態になり、「移動」で別の予定や未分類に移せる。長押しで拡大表示。
- ③で「この内容で追加」を押したら、アップロードは④の裏で進める。

### 6.3 振り分けのルール

入力は、写真（撮影時刻、位置情報があれば位置も）と、旅程の予定（日付・時刻・緯度経度）。

1. **期間外の写真を除く**: 撮影日が `start_date` 〜 `end_date` の範囲外なら「期間外」として除外する（③で含めることもできる）
2. **撮影時刻がない写真**（EXIFがないもの）→ 未分類
3. **位置で決める（`auto_geo`）**: 写真に位置情報があり、同じ日の予定のうち半径1km以内に緯度経度を持つものがあれば、一番近い予定にする。予定は時間どおりに進まないことが多いので、位置を時刻より優先する
4. **時刻で決める（`auto_time`）**: 同じ日の「時刻がある予定」を時刻順に並べ、各予定の担当時間を「開始の15分前 〜 次の予定の開始の15分前」とする
   - 最初の予定より前: 最初の予定の開始60分前以降ならその予定、それより前なら未分類
   - その日最後の予定: その日の終わり（翌朝4:00まで）
   - 時刻のない予定は時刻では振り分けない（位置だけ）
5. どれにも当てはまらなければ未分類（`unassigned`）

しきい値（1km、15分、60分、4:00）は定数にまとめ、修正率を見て調整する。

### 6.4 未分類の写真の扱い
- 未分類の写真は、しおり画面の日ごとの見出しに「📷 未分類 4枚」として出し、あとから振り分けられるようにする
- 最終的に未分類のまま残っても、生成するムービーやアルバムには「その日のひとコマ」として含める（別仕様書）

## 7. B案：「今」画面からワンタップ撮影

### 7.1 ホーム画面からの起動

**しおりごとにホーム画面へ追加する**
- しおり画面に「このしおりをホーム画面に追加」を出す
- しおりごとの `<link rel="manifest">` を返し、`start_url` を `/group/{token}/travelplanner/{id}/now`、アプリ名をしおり名（例：「沖縄旅行」）にする
- アイコンをタップすると、その旅の「今」画面が直接開く

**全体用のマニフェストも変える**
既存の `src/app/manifest.ts` の `start_url` を `/now` に変える。`/now` は `localStorage` の `shiori_*`（`RecentPlans` と同じデータ）から旅行期間中のしおりを探して、次のように振り分ける。
- 1件 → そのしおりの「今」画面へ
- 複数 → 選択画面
- 0件 → トップページへ

**案内の出し方**
旅行の3日前〜前日にしおりを開いたとき、「旅行中すぐ撮れるようにホーム画面に追加しよう」とシートで案内する。iOS では追加の手順（共有 → ホーム画面に追加）を図で見せる。

**要検証**
- iOS でホーム画面に追加したアプリは、Safari と `localStorage` が共有されない。そのため `/now` 方式は最初は空振りしやすい。しおりごとのマニフェストを主な導線にする
- iOS の「ホーム画面に追加」が、しおりごとのマニフェストの `start_url` を使うかどうかは実機で確認する

### 7.2 「今」画面

パス: `/group/[token]/travelplanner/[travelPlannerId]/now`

```
┌─────────────────────────────┐
│ 沖縄旅行            Day 2 / 3 │
│                    [しおり ▸] │
├─────────────────────────────┤
│                             │
│   いまの予定                  │
│  ◀  12:30                ▶  │
│     錦市場でランチ             │
│     📍 錦市場                │
│                             │
│   つぎ 14:00 清水寺           │
│                             │
├─────────────────────────────┤
│ さっき撮った写真              │
│ [■✓][■✓][■↑][■⏳]           │
│ 未送信 1枚（電波が戻ったら送信）│
├─────────────────────────────┤
│                             │
│   ┌───────────────────┐     │
│   │    📷  撮る        │     │  ← 親指が届く位置に大きく
│   └───────────────────┘     │
│   [🤳 自撮り]  [🖼 アルバム]   │
└─────────────────────────────┘
```

**「いまの予定」の決め方**
- 今日の予定のうち、開始時刻が現在時刻以前で一番遅いもの
- まだ最初の予定より前なら最初の予定（「これから」と表示）
- 今日が旅行期間外なら「今」画面は出さず、しおり画面へ移動する

**予定の切り替え**
- ◀ ▶ またはスワイプで、前後の予定に切り替えられる（予定が押しているとき用）
- 手動で選んだ予定は、次の予定の開始時刻を過ぎるまで優先する

### 7.3 撮影の流れ

1. 「📷 撮る」を押すと `<input type="file" accept="image/*" capture="environment">` で標準カメラが開く（自撮りは `capture="user"`、アルバムは `capture` なしで複数選択可）
2. 撮影し、OSの「写真を使用」を押す
3. 画面に戻った瞬間に「錦市場でランチに追加しました ✓ [取り消す]」と表示する。アップロードの完了は待たない
4. `taken_at` は撮影した時点の端末の現在時刻、`assign_method='capture'` として、5章の送信待ちの列に入れる

アイコンを開いてから撮影を終えるまで4タップ（アイコン → 撮る → シャッター → 写真を使用）になる。

「写真を使用」の確認はOS側の画面なのでWebからは省略できない。アプリ内に独自のカメラ（`getUserMedia`）を作れば連写や2秒動画にもできるが、それは次の段階で検討する。

### 7.4 電波がないとき
- 撮影と送信待ちの列への保存は、通信なしでも完了する
- 「今」画面そのものを圏外で開けるようにするには Service Worker（アプリをブラウザの裏で動かす仕組み）でのキャッシュが必要。M3で対応する。M2では「一度開いた画面を開きっぱなしにしておけば撮れる」状態を最低ラインとする

## 8. しおり画面での写真表示

- **予定のカード**: 写真があれば「📷 5」のバッジを出す
- **予定の詳細シート**（`ActivityDetailSheet` / `ActivityDetailModal`）
  - 「みんなの写真」欄を追加し、3列のグリッドで表示
  - タップで拡大、左右スワイプで送る
  - 撮った人の名前と時刻を表示する
- **写真の削除**: 撮った本人の端末（`uploader_device_id` が一致）からのみ削除できる。それ以外の人には「非表示にする」（その端末でだけ隠す）を出す → 決めてほしい事項1

## 9. プライバシー・法務

- 初めて写真を追加するときに、次の2点を一度だけ表示し、同意してもらう
  - 「このしおりのリンクを知っている人は写真を見られます」
  - 「写真の位置情報は保存しません」
- プライバシーポリシーに「利用者が投稿した画像」の項目を追加する（法務担当に改定案を依頼）
- 共有プレビュー（`SharePreview.jsx`）や OGP 画像には、利用者の写真を使わない
- しおりを削除したとき、DBの行は連動して消える（CASCADE）が、Cloudinary 上の画像は残る。旅程単位のフォルダ（`travel-planner/media/{itineraryId}`）ごと消す後片付けの処理を用意する

## 10. 上限とコスト

| 項目 | 初期値 |
|---|---|
| 1しおりあたりの写真上限 | 300枚 |
| 1枚あたりの最大サイズ（縮小後） | 2MB |
| 一度に取り込める枚数 | 100枚 |

- 1しおりあたり 約500KB × 300枚 ≒ 150MB が上限の目安になる
- Cloudinary の無料プランは月25クレジット（1クレジット ≒ 保存1GB、転送1GB、変換1,000回のいずれか）。利用が増えると有料プランが必要になる
- 保守運用担当が、月次で使用量を監視する
