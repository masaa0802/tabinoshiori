01 CRITICAL 保守運用

無認証で全データを操作できるAPI経路が2つある

src/app/api/graphql/route.ts は、クライアントが自称する operationName の文字列だけを見て認可を判定し、クエリ本文を検査せずに管理者権限付きで Hasura へ転送している。次の1行を送るだけで、認証なしに全グループのトークンと全旅程が抜ける。

{"operationName":"InsertGroup",
 "query":"query InsertGroup { groups { id name token } }"}

同じ手口で delete_* も通る。加えて src/app/api/delete/route.ts には認証コードが1行もない。/api/upload と /api/cache-image にはトークン検証があるのに、削除APIだけ欠落している。URLを知る者は誰でも他人のアップロード済みPDF・画像を永久削除できる。

この2つは連鎖する。前者で全トークンとファイルURLを列挙し、後者で全削除まで到達できる。統括が実コードを読んで裏取り済み。

推奨アクション本日中に着手。削除APIにトークン検証を追加し、GraphQL側は文書を parse() して operation 種別を検証する許可リスト方式へ。暫定措置として削除APIを 503 で塞ぐ選択肢もある。
02 HIGH 保守運用

本番Hasuraの管理シークレットが平文でコミットされている

apply-to-production.js ほか計7ファイルに、同一の64文字シークレットが定数として直書きされ、git管理下にある。履歴にも残っている。READMEと仕様書にはローカル開発用の別の値が平文で載っている。

統括による補足。リポジトリは private、フォーク0件を確認した。全世界に露出している状態ではないため、保守運用が挙げたCriticalからHighに落とす。ただしシークレットはgit履歴に残り、リポジトリへのアクセス権を持つ者と連携している外部サービスに渡っている。

推奨アクション本番シークレットをローテーション。ファイルを消すだけでは履歴に残るので無意味。7ファイルを環境変数参照へ書き換える。履歴の書き換えはローテーション後であれば必須ではない。
03 HIGH サポート・企画開発

LPが約束している共有機能が、アプリ本体に存在しない

サポートと企画開発が独立に同じ結論に達した。LPは「URLひとつでグループ全員に共有」を主要機能として掲げ、FAQ・構造化データ・OGPでも同じ約束をしている。しかししおり画面に共有ボタンもURLコピーもない。

src/ 全体で clipboard と navigator.share を検索しても、LPのモックUI以外にヒットしない。共有UIの SharePreview.jsx は実在するが、呼び出し元の ItineraryCard.jsx ごとどこからも import されていない死にコードになっている。

登録不要のアプリなので、幹事が送るURLが唯一の新規ユーザー流入経路。ここが詰まると利用が幹事1人で止まる。

推奨アクション規模S、半日で終わる。承認があれば最優先で実装する。

  • npm run lint は失敗。Next.js 16 で next lint が廃止され、スクリプトが死んでいる。「通っている」のではなく「実行されていない」。直接実行するとエラー21件。

Critical

  • GraphQL APIの認可バイパスと削除APIの認証欠落（最重要3件の01）。
  • 本番シークレットの平文コミット（最重要3件の02）。
  • Next.js の未認証RCE。Image Optimization API のAVIF処理。npm audit fix で解消できる。

High

  • 共有トークンが Math.random() でクライアント生成。暗号論的に安全でなく、値を攻撃者が任意指定できる。このトークンが旅程の唯一の認証情報。
  • トークンに所有スコープがない。自分で1つ旅程を作れば有効なトークンが手に入るため、上記を直しても全ユーザーのデータへ横断アクセスできる。
  • 管理画面のログインにレート制限がなく、セッショントークンが固定値。一度漏れるとサーバ側から失効させる手段がない。

Medium の主なもの

  • プロキシAPIが cloud_name を検証せず、他人のCloudinaryのファイルを自社ドメインから配信できる。フィッシングに使える。
  • 画像キャッシュAPIのSSRFガードが広すぎ、公開GCSバケットの任意ファイルを取得できる。サイズ上限もない。
  • レート制限が1ルートにしかなく、その実装も x-forwarded-for を信用するため偽装で回避できる。
  • 管理シークレットの環境変数名が NEXT_PUBLIC_ にフォールバックしている。クライアントから1行参照されただけでJSバンドルに埋め込まれる。

今日の3案

  • 共有ボタン（規模S）。新機能ではなく、宣伝している機能の導線欠落。共有実行率を計測する仕組みもないので、GAイベントを同時に入れる。
  • 立て替え・割り勘の精算（規模M）。予算タブに支払者の概念が一切なく、精算作業はLINEと電卓に漏れている。DBには受け皿がすでにある。budgets.paid_by（コメントに「支払った人の名前」）、users、group_members、Hasuraのリレーション定義まで存在するのに、クエリが選択していない。設計時に想定されていて作られなかった機能。旅行後にアプリを開く理由を作る唯一の候補でもある。
  • しおりの公開によるSEO受け皿（規模L）。SEOチェックリスト自身が「検索流入の入口が実質トップページ1枚のみ」と書いている。個人情報を除いた読み取り専用ページを生成し、そこだけ noindex を外す。効果が出る期間は読めないので数字の約束はしない。

深掘りした割り勘機能

  • v1は登録メンバー全員で均等割りに割り切る。一部メンバーだけで割るのは現場でよく起きるがテーブルが増えるのでPhase 2へ。
  • 新規テーブルなし。budgets に paid_by_member_id を1本足すだけ。既存クエリへの追加も破壊的変更にならず、段階リリースできる。
  • 精算計算はサーバに置かず src/lib/settlement.ts の純粋関数に。送金回数は最大でもメンバー数−1回。端数の行き先を画面に明記する。
  • 境界条件を明示して扱う。メンバー0人・1人、支出0件、全員差額0、支払者不明のみ、通貨混在。

棚卸しで分かったこと

  • ブログ機能は仕様書が完成しているのに src/ に一行もない。新案ではなく着手待ちの承認済み設計として別枠で扱うべき。
  • 京都のサンプルデータをハードコードした未使用画面が残っている。削除可否の判断が必要。
