## 今日の最重要3件

### 1.【Critical】`/api/graphql` と `/api/delete` が無認証で全データを操作できる

統括が実コードを読んで裏取り済み。推測ではない。

- `src/app/api/graphql/route.ts` は、クライアントが自称する `operationName` の文字列だけを見て認可を判定し、クエリ本文を検査せずに管理者権限付きで Hasura へ転送している。`{"operationName":"InsertGroup","query":"query InsertGroup { groups { id name token } }"}` を送るだけで、認証なしに全グループのトークンと全旅程が抜ける。同じ手口で `delete_*` mutation も通る。
- `src/app/api/delete/route.ts` には認証コードが1行も無い。`/api/upload` と `/api/cache-image` には `x-group-token` 検証があるのに、削除APIだけ欠落している。URLを知る者は誰でも他人のアップロード済みPDF・画像を Cloudinary から永久削除できる。
- この2つは互いに連鎖する。前者で全トークンとファイルURLを列挙し、後者で全削除まで到達できる。

**推奨アクション**: 本日中に着手。`/api/delete` にトークン検証を追加、`/api/graphql` は文書を `parse()` して operation 種別とフィールドを検証する許可リスト方式へ。暫定措置として `/api/delete` を一時的に 503 で塞ぐ選択肢もある。

### 2.【High】本番 Hasura の管理シークレットがリポジトリに平文でコミットされている

`apply-to-production.js` ほか計7ファイルに、同一の64文字シークレットが定数として直書きされ、git 管理下にある。履歴にも残っている。README と `docs/SPECIFICATIONS.md` にはローカル開発用の別の値が平文で記載されている。

統括による補足: リポジトリは **private、フォーク0件** であることを確認した。したがって全世界に露出している状態ではなく、保守運用担当が挙げた Critical から High に落とす。ただしシークレットは git 履歴に残り、リポジトリへのアクセス権を持つ者と連携している外部サービス（`.coderabbit.yaml` 等）に渡っている。ローテーションは実施すべき。

**推奨アクション**: 本番 admin secret をローテーション。7ファイルを環境変数参照へ書き換え。履歴の書き換えは、ローテーション後であれば必須ではない。

### 3.【High】LPが約束している共有機能が、アプリ本体に存在しない

サポートと企画開発が独立に同じ結論に達した。

- LP（`src/app/page.tsx`）は「URLひとつでグループ全員に共有」を主要機能として掲げ、FAQ・構造化データ・OGPでも同じ約束をしている。
- しおり画面に共有ボタン・URLコピーのUIは1つも無い。`src/` 全体で `clipboard` と `navigator.share` を検索しても、LPのモックUI以外にヒットしない。
- 共有UIのコンポーネント `src/components/SharePreview.jsx` は実在するが、参照元の `src/components/ItineraryCard.jsx` 自体がどこからも import されていない死にコードになっている。
- 登録不要のアプリなので、幹事が送るURLが唯一の新規ユーザー流入経路。ここが詰まると利用が幹事1人で止まる。

**C-2. `/api/graphql` の認可が `operationName` 文字列だけで判定されており、完全にバイパス可能**
`src/app/api/graphql/route.ts:12, 54-84, 86-93`。`PUBLIC_OPERATIONS = {'InsertGroup','InsertItinerary'}` に一致すればトークン検証をスキップするが、検証しているのはクライアントが自称する `operationName` だけで、`query` 本文は一切検査せず、そのまま admin-secret 付きで Hasura に転送している。
被害: `{"operationName":"InsertGroup","query":"query InsertGroup { groups { id name token } }"}` を投げるだけで、認証なしに全グループのトークンと全旅程データを吸い出せる。任意の `delete_*` / `update_*` mutation も実行でき、無認証でのデータ全削除が成立する。
対処: `graphql` パッケージで document を `parse()` し、実際の operation 種別・名前・フィールドをサーバ側で検証する許可リスト方式へ。最低限、パブリック経路は事前定義クエリとの完全一致か persisted query に限定する。

**C-3. `/api/delete` に認証が一切ない**
`src/app/api/delete/route.ts:19-41`。`x-group-token` の検証コードが存在しない（upload / cache-image には実装されているのに、このルートだけ欠落）。
被害: URLさえ分かれば、誰でも全ユーザーのアップロード済みPDF・画像を Cloudinary から永久削除できる。復旧手段なし。`extractFromUrl` が返す `resourceType` は攻撃者がURLで制御でき、L33の型アサーションは実行時の保証がない。

5. **ポリシーに「実際にはやっていないこと」が書かれている**。第2条「利用登録をする際に…銀行口座番号、クレジットカード番号、運転免許証番号などをお尋ねすることがあります」、「提携先（広告主）から取引記録や決済情報を収集することがあります」、第3条「有料サービスにおいて利用料金を請求するため」。実際は登録なし・決済なし・提携先からの収集なし。利用目的の特定（法17条）を欠くと評価されうるうえ、実際に取得しているアップロード画像・位置情報・アクセス解析情報が一切書かれていないという二重のズレ。
6. **共有リンクの性質とリスクがどこにも説明されていない**。`Math.random()` 2回連結のトークンのみでアクセス制御し、パスワードも有効期限もなく、URLを知る者は誰でも閲覧・編集・アップロード・削除ができる。予約票PDFという機微性の高い情報を扱う以上、安全管理措置（法23条）の観点から、実装の是正と規約での性質説明の両方が必要。
7. **`/api/delete` にアクセス制御がない**。個人データの滅失・毀損の防止（法23条）に直結。規約文言では手当てできない実装側の不備。

**中リスク7件**: Googleフォームの利用事実・取得項目・利用目的が未記載（8）／位置情報の取得が未記載、地図画面表示と同時に無条件で `getCurrentPosition()` を呼んでいる（9）／訪問スポットの座標・写真を保存し管理画面で分析していることが利用目的に入っていない（10）／利用者が同行者の個人情報を入力・アップロードすることへの手当がない（11）／保存期間・削除方法が未定義でアップロードファイルは無期限保存、localStorageへの保存も未記載（12）／全部免責条項が消費者契約法8条により無効となるおそれ、第4条2項・第6条2項・第8条1項に但書がない（13）／規約変更条項が「通知することなくいつでも変更できる」で民法548条の4の要件を満たさない（14）／広告掲載に関する条項が利用規約側にない（15）。

**低リスク2件**: ステマ規制は現行のAdSlotが「広告」ラベルを明示しており現時点で問題なし。ただし `AdSlotInFeed` は「周囲のカードと同じ見た目にしつつ」という設計で、ラベルが `text-[10px] text-gray-400` と極めて小さく薄いため、有効化時は要注意（16）／プライバシーポリシーの「最終更新日」が `new Date()` による動的生成で、改定していない日もアクセス日が最終更新日として表示される。利用規約側はハードコードで不整合（17）。
